// 06 PAYFLOW · P2P PAYMENTS ● LIVE +

A P2P and QR-payments app built around one idea: a payments product can't survive a naive retry. Every transfer requires an idempotency key, so a request that times out and gets retried replays the original result instead of moving money twice. Auth tokens never touch localStorage, and every field on the transfer DTO is whitelisted server-side rather than silently passed through.

Stack: Vue 3 · TypeScript · Pinia · NestJS · Passport JWT
Core mechanic: idempotency-key transfers, integer-yen math, hand-rolled virtual scrolling

The retry path that actually matters:

// Second attempt, same Idempotency-Key header
const cached = store.get(idempotencyKey);
if (cached) return cached;          // replay — balance untouched

const result = transfer(sender, recipient, amountMinor);
store.save(idempotencyKey, result); // first time only
return result;

// 05 PULSEBOARD · LIVE MONITORING ● LIVE +

A live transaction-monitoring dashboard built to demonstrate frontend performance work directly instead of just claiming it. The feed table is virtualized so a few-thousand-row feed never costs more than what's on screen, the chart bundle is code-split and loaded on demand, and a Web Worker handles the rolling aggregation off the main thread. A panel on the dashboard shows the page's own live Core Web Vitals — the same numbers a RUM tool like New Relic Browser reports.

Stack: React 18 · TypeScript · react-window · Express · WebSocket
Core mechanic: virtualized rendering, code-split charts, Web Worker aggregation, live Web Vitals

The fraud rule that flags a burst:

// 3+ transactions from the same user inside 60s
const recent = history.filter(t =>
  t.userId === tx.userId && tx.timestamp - t.timestamp <= 60_000
);
const flagged = recent.length >= 3 || tx.amountMinor > 300_000;

// 04 MUSIC LIBRARY · SQL ● LIVE +

A normalized SQLite catalog of my Spotify Liked Songs. Full ETL pipeline, analytical Jupyter notebook, and an in-browser SQL terminal running SQLite via WebAssembly. Doubles as a sound-design reference — query for tempo, key, and genre to find candidate tracks for whatever I'm scoring.

Stack: SQLite · Python · Spotify Web API · sql.js (WASM)
Schema: 10 tables in 3NF, 7 indexes, 2 convenience views

The query I actually use:

-- Find chill reference tracks near 75 BPM in a minor key
SELECT track_name, primary_artist, ROUND(tempo, 1) AS bpm, key
FROM v_tracks_full
JOIN user_likes USING(track_id)
WHERE tempo BETWEEN 70 AND 80
  AND mode = 0
ORDER BY ABS(tempo - 75)
LIMIT 10;
